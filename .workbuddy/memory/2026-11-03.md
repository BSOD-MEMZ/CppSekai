# 2026-11-03

## 设置窗口颤抖（真 bug，极限环）

`tabCardH[tab]` 的"按内容反推高度"没有不动点：

```
stored = cardH + (used + 10s) - view
```

`view` 是 ImGui 把 child 高度**取整**后的值，实测 `used` 恒 603、`view` 在 **615/616 交替**，
于是 `cardH` 在 **783.8 ↔ 784.75** 之间以 60Hz 来回 —— 卡片底边和 `dropShadow` 每秒抖 60 次。

修法（`main.cpp` 设置卡片内容收尾处）：`std::round()` 落整像素 + **1.5px 死区**
（`|wanted - cardH| < 1.5` 就不动，`stored = cardH`）。七页实测各自定住：
804 / 699 / 707 / 784 / 652 / 765 / 521，`CPSEKAI_UI_TRACE` 每页只剩两个 view 值
（首帧 811 = 默认 780 卡，然后收敛值），`scrollMax=0` 全都不滚。

**教训**：任何"测量 → 回写 → 再测量"的反馈环，只要测量值会被取整/量化，就必须带死区，
否则一定有极限环。这次和选曲那次的 `slotHeights` 是同一类问题的两种表现（那边是多个写者
抢一个值，这边是单一写者的量化抖动）。

## 猜歌三件事

### 1. 点击卡住 → 分帧建题库

根因：`newGuessQuestion()` 在点击那一帧同步建整个题库。最贵的一段是
"别人的曲名不能正好是这个别名"这条规则——(别名 × 全部标题) 双层循环，每一对都
`toLower(titleFor(id))` 造一份临时 string，12.9k × ~500 = **6.4M 次**。

改法：
- `gTitleLowerIndex`（小写曲名 → 曲 id 们）把那段变成一次哈希查找；
- `startGuessPoolBuild()` / `tickGuessPool()` 按 **~3ms/帧** 增量推进，进度写
  `gGuess.loadingPercent`，卡片先画出来显示「正在准备题库…」+ 进度条；
- 卡片关了也继续建，下次点直接能玩；
- 收尾时自己 `newGuessQuestion()`。

实测：**cpu 15~30ms 摊在 5~8 帧**（每帧 ≤4ms），可用别名仍 **11876**（= 改动前基线，
说明哈希替换是等价的）。日志 `[guess] pool built: cpu X ms over N frame(s), wall Y ms` ——
**两个数都要看**：wall 会被启动那几帧（本来就要 200ms 加载资源）拉到 300ms+，
只看 wall 会以为构建很慢。

凑不出题时不再 `open = false`（那看起来像按钮没反应），改成 `gGuess.unavailable`，
卡片留着写「没有可用的题库」。

### 2. 入场/出场动画没了

根因是**同一个**：`if (gGuess.open && options.size() == 4)` 这个门。

- 关的时候那一帧就停止调用 `beginCard()` → 出场动画没有；
- 更糟：`beginCard` 只有在**关闭动画真的播完**（`t` 走到 0 → `st.ended = true`）之后，
  下次 open 才会把 `t` 重置成 0。所以第一次点有入场、**之后永远没有**。

改法：照 `keymapCardAlive` / `eulaAlive` 的老套路加 `gGuessAlive` —— `open` 只当目标态，
`beginCard()` 返回 false 时才落下来。

验证（临时 `CPSEKAI_GUESS_CLOSE_AT=<sec>[,<reopenSec>]`，验完已删）：
- 关闭后 60ms 那帧卡片缩到 **81%** 且半透明 → 出场在播；
- 关闭 → 1.40s 重开 → 1.46s **84%**、1.52s 99.7%、1.60s 100% → **第二次打开也有入场**。
- 踩坑：第一版测试把 close 和 reopen 都设成 1.0，同一帧里 open=false 又 open=true，
  等于没关，三次截图全是满尺寸 —— 参数一定要留够间隔（关闭动画 0.16s）。

### 3. 长曲名选项冲出胶囊

`guessOptionPill()` 里 `dl->AddText` 直接用原标签，没有宽度约束，
「ワールド・ランプシェード [reunion]」这类会横穿整张卡片。改成先过
`ellipsize(font, fontSize, label, size.x - 18s)`（和歌曲列表同一个 helper，
按 UTF-8 码点裁 + 补 …，构造上保证宽度 ≤ 上限，不需要截图验证）。

## 血量归零：LIVE CLEAR"又要播又不播" + 结算第一屏"损坏"（commit b81a8c5）

两个症状是**同一件事**：横幅和结算屏都没坏，是两条黑场逻辑打架。

### 根因
2026-11-01 把横幅改成"不看血量统一播"（失败局也出 LIVE CLEAR），但
`else if (!clearedSoFar)` 的普通黑场分支没删。失败局时间线：
1. 曲末前 1 s：横幅未 armed，走普通黑场分支，`songEndBlackout` 被推向 1 → 画面提前全黑；
2. 曲末：横幅 armed，切到 `max(banner.blackout(), u)` —— **max 保留旧值**，那个 1 永远
   压着横幅 → LIVE CLEAR 字落在全黑上，观感"播了又像没播"；
3. u 推到 1 黑透 → 切结算 → summary 显示 LIVE FAILED（黑场里突然换内容，观感"第一屏损坏"）。

cleared 局没有那个分支，所以只有失败局看得见 —— 和"小曲库选中卡片颤抖"同类：
**分支只影响特定路径**的回归最隐蔽。

### 修法
删掉 else-if 普通黑场分支 + `clearedSoFar`（唯一消费者）。横幅 armed 后黑场完全归
横幅的 u 曲线；切结算前黑透照旧由 bannerFadeEnd 保证，summary 的 fromBlack 不受影响。

### 复现/验证手法（可复用）
- 失败局无头复现：`profiles/default.json` 的 settings.initialLife=100（下限）+
  **不加 --auto**（无输入全 miss，2 miss 扣光）+ `--result-at <sec>` 提前切。
- ⚠ `--screenshot-time` **同时喂两个屏幕**：演奏屏 `songTime >= t`，Result 屏
  `resultElapsed >= t`。抓 Result 的 summary（<2.6s）要让演奏屏先切走。
- ⚠ `--result-at` 提前切时 bannerFadeStart 仍按曲长算 → 结算要等几十秒。
  用 `CPSEKAI_BANNER_T=<大值>` 冻结横幅时钟（blackout/draw 内部 min(mTime,kDuration)，
  画面定格在横幅终态），`bannerFinished` 立即满足。**画面会带 scrim 0.55**，量亮度挑对时机。
- 亮度对比用中心区域均值（pngcrop.read_png），比目测截图可靠。
- `--result-preview` 新增 `CPSEKAI_RESULT_FAIL=1` 预览失败结算（LIVE FAILED、无
  SCORERANK 牌）。failed 贴图 `result/livefailed_wh.png` 1352x166（比 liveresult 宽 80px）。

### 结果
- 修复前 songTime 6.4（横幅前）全画面亮度 2.8（纯黑）；修复后 37.7；横幅出现时 26.8，
  LIVE CLEAR! 清晰、舞台半透明可见、血量 0 的暗角保留（设计内）。
- 真实流程 summary 1.2s 与 --result-preview 一致，无其它损坏；--auto 回归 miss=0 / 49 连击。

### 教训
改共享状态（songEndBlackout）的多分支逻辑时，先画出每个 state 下每帧谁写它；
删行为时把注释一起删（AGENTS.md 里"失败不播横幅"两处过时说明这次才更正）。

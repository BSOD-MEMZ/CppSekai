## 09:00-09:40 两件用户需求：多人开局倒计时删掉 + 失血阴影几何修好

用户原话：「去掉游戏开始的那个倒计时，失血阴影的显示也有问题」。问了一句确认，
倒计时指的是**多人房间里「即将开始 5.8s」那个大数字**（单机开局本来就没有倒计时，
截图 `--screenshot-time -0.5` 确认过：只有舞台淡入）。

### 1) 多人开局不再有倒计时（改成"加载完就开"）

**旧行为**：房主一开始就把起奏时刻定成 `now + 5.8s`（`beginCharging`），全房在那干等
5.8 秒，选曲界面上盖一层 + 中央大数字倒计时。**实测等待固定 5.8s，跟加载快不快无关。**

**新行为**（charge 分两段，靠 `startCounter == 0` 区分）：
- 加载段：房主 `beginLoading()`（epoch++、phase=Charging、**不写 startCounter**）；
  每个窗口加载完自己的谱面 `setSeat(PartySeatLoaded)`（新加的座位状态）。
- 武装段：房主 `allLoaded()`（非 Lobby 座位全是 Loaded）→ `armStart(now + 0.8s)`
  （**不动 epoch**，否则成员以为换了一轮）。
- 看门狗 `kPartyLoadTimeoutSec = 6.0`：有人卡住/加载失败时照常武装，不会整房停死。
- 房主强制开始（第二次按确定）也走 `beginLoading()`：没确认的窗口立刻退成 Lobby 让开。
- 删掉选曲界面上的遮罩 + 大数字；面板状态行只写 `谱面加载中…` → `即将开始`（不带数字）。
- 房主自己加载失败时 `releaseSong()` 回大厅，成员按"房主已放弃本曲"回列表（原来会停死）。

**实测**：`[party] start in 0.80s (every chart loaded; the room waited 0.24s for the loads)`
—— smoke 谱加载 0.2s，总等待 ≈1.0s，比旧版省约 4.8s。
回归：`bash .workbuddy/tools/mp_verify.sh` **三轮全 PASS**（同一 start counter / 时钟偏差
中位 3.3ms 最差 6.4ms / 暂停冻结 0ms / 结算与重开房间），另跑了"房里只有一人"路径。

**坑（记在 AGENTS.md 了）**：
- 成员第一次看到 charge 时的 `late` 判定必须带 `startCounter != 0`。QPC 是个大正数，
  裸写 `now >= startCounter` 会在加载段把所有窗口判成"错过开局"。
- `armStart` 只在 `phase == PartyCharging` 时写，否则会把已释放的房间复活；
  房主侧 `mpArmedEpoch` 保证一轮只武装一次（重复武装会把时刻一直往后推）。
- **帧时钟不能用来量加载耗时**：加载在某一帧里同步发生，`uiClock` 那一帧不推进，
  量出来是 0.03s。改用 QPC（`counterToSeconds`）才是真时间。
- 迟到的窗口仍然正确入局（时钟锚在共享 QPC 上，只是少看一段开幕卡），不用额外踢人。

### 2) 失血阴影（damage vignette）几何修好

**旧实现**：四角各一块 `min(w,h)*0.55` 的方块。16:9 上 `2*0.55h = 1188 < 1920`，
于是**上下边缘正中留了约 880px 的亮带完全没被压暗**，且方块边界处 50% 黑 → 0 是硬断崖。
实测（1920x1080，`CPSEKAI_VIGNETTE=0.85`）：y=8 一行上 alpha 127 在 x=594、0 在 x=614。

**新实现**：**四条整边条**，各自垂直自己那条边渐隐，四角两条叠加自然变最暗。
`rc = min(w,h)*0.42`，单条峰值 `120*damageVig`（角落 ≈1.6 倍）。
实测：上/下边缘中段 alpha ≈92（原来 0），四角 ≈134，屏幕中心 0，且逐像素扫无断崖。

**注意 `ImDrawList::AddRectFilledMultiColor` 的四个角顺序是
（左上、右上、**右下**、左下）**——下边两个不是阅读顺序。旧代码注释写错了顺序，
但因为只用了对角两个顶点，效果侥幸是对的。新代码要按真顺序传。

**新增调试探针**：环境变量 `CPSEKAI_VIGNETTE=<0..1>` 把阴影冻结在这个强度上，
掉血需要真人漏接、`--screenshot` 造不出来（`--test-hits` 是"帮打"，life 不掉）。
对照图手法：同一时刻跑 `=0` 与 `=0.85` 两张，用 PIL 按 `1 - vig/zero` 反算 alpha 分布。
已写进 CLI.md 第五节。对比图：`build/shots/vig_compare.png`。

### 验证手法
- 截图量 UI 一律用 `--screenshot`（GL glReadPixels，方向无歧义）；
  **同一时刻两次运行的画面会有 1 帧级差异**（音符/特效位置），逐像素比 alpha 时要把

## 踩坑：差点弄丢一个素材（自作自受，已完整恢复）
`assets/ost/` 里那个结算 BGM 在**磁盘上的名字是「キミだけの軌跡.mp3」，而 git 里记的是
「キミだけの足跡.mp3」**（用户自己改了错字，还没 add）。我为了从 git 恢复它，
手打路径 `git cat-file -p HEAD:assets/ost/キミだけの軌跡.mp3 > 同名文件` ——
**shell 先执行 `>` 把目标文件截成 0 字节，git 随后才报"not in HEAD"**，于是把用户的
1.5MB 文件清空了（原内容还在 git 对象里，用 `git ls-files -z` 拿到真名后
`git cat-file -p` 恢复，字节数 1583381 对得上）。
教训（写给以后的自己）：
- **永远不要手打含非 ASCII 的路径去 `>` 重定向**；先 `cat-file` 到 `/tmp` 核对大小，再 `mv`。
- 这个仓库里**磁盘文件名可能和 git 里的名字不一致**（用户会手改名字），
  `git cat-file <rev>:<path>` 失败且报"exists on disk, but not in HEAD"就是这个信号，
  此时用 `git ls-files -z` 拿真名，不要照着屏幕上看到的名字敲。
- `git status` 的 ` D` + `??` 成对出现 = 用户自己在改名，别当成"文件丢了"。

## Win7 启动失败 —— 「无法定位程序输入点 GetSystemTimePreciseAsFileTime」（已修）

用户在 Win7 机器上跑，加载阶段就弹「无法定位程序输入点 GetSystemTimePreciseAsFileTime
于动态链接库 KERNEL32.dll 上」。查下来根因不在业务代码，在工具链：

- 新工具 `.workbuddy/tools/pe_imports.py`（纯 stdlib 解析 PE 导入表，含 delay-import）。
  三个 PE 的结论：**cppsekai.exe / chartdl.exe 各只有 1 个 Win8+ 导入**（就是这个），
  SDL2.dll 完全干净。其余 94 个 KERNEL32 导入（SRWLock/FlsAlloc/InitOnceExecuteOnce/
  GetTickCount64/RtlVirtualUnwind…）都是 Vista 基线，`GetFileInformationByHandleEx` /
  `SetFileInformationByHandle` 也是 Vista 就有（差点被我误报成 Win8）。
- 来源：zig 自带 libc++ 的 `lib/libcxx/src/chrono.cpp`，编译时 `_WIN32_WINNT=0x0a00`
  → `std::chrono::system_clock::now()` 走 Win8 分支**静态导入**。项目里一处 `system_clock`
  都没用，连 `<iostream>` 空程序都会中招（libc++ 内部引用），业务代码绕不开。
- 试过没用的三条：`-D_WIN32_WINNT=0x0601`（只管我们自己的 TU，libc++ 预编译的）；
  同名强符号顶掉（zig 直接拿 DLL 当链接输入 → `duplicate symbol … defined at KERNEL32.dll`）；
  `-Wl,--allow-multiple-definition`（zig 不认这个参数）。
- 修法：`build.sh` 顶部幂等 sed 两处（+ 删一行续行），强制走 libc++ 的运行时探测分支

## 拖动窗口不刷新 —— 找到真根因并修好了（窗口子类化）

上一条我把 `[sync]` 的行数当"泵没被挂住"的判据，**读错了**：那 1.93s 的 qpc 跳变就是
"整整一帧卡在拖动里"。这次加了**常驻探针**（帧体开头，不需要环境变量，只在几何变化/长帧时
打印）：`[frame] geometry changed: 56 frame(s)/s, longest frame 2264 ms, window moved 392 px`
—— 最长帧 ≈ 拖动时长（2.1s 拖 → 2264ms）= 泵被挂住的签名。

**真根因（查 SDL2 源码得到）**：`SDL_SetWindowsMessageHook` 的钩子是在 **`WIN_PumpEvents`
（SDL 自己的事件泵）**里调的，**不在窗口过程里**。模态循环期间我们的泵不跑 → 钩子永远不被调用
（全程 24 条消息，没有 ENTERSIZEMOVE/WM_MOVING）。所以上一版"方案 a"的触发点根本不存在，
它只在伪造消息的合成测试里跑通过 —— 又一次"没验证前提就动手"。

**修法**：`main.cpp` 里 `runFrame` 之后那块改成**子类化窗口过程** ——
`SetWindowLongPtrW(GWLP_WNDPROC)` 换成我们的过程，原过程（SDL 的）存下来，末尾
`CallWindowProcW` 转回去；状态放**窗口属性**（`SetPropW`，SDL 自己也这么存窗口数据），
所以没有新增模块级全局。`WM_ENTERSIZEMOVE` 开 16ms 定时器；`WM_MOVING/WM_MOVE`、
`WM_SIZING/WM_SIZE`、我们的 `WM_TIMER` 各喂一帧；`depth` 挡嵌套、8ms 下限防"每个鼠标消息一帧"。

**实测（Win11，SendInput 拖 2.1s / 280px）**：`127 frame(s) served (moving=126 sizing=0 timer=1)`
≈ 60fps，探针最长帧从 **2264ms → 19~29ms** ✓。Win10 22H2 那边更经典，消息一定会送到窗口过程。

**验证工具**：`dragwin.exe`（SendInput 真拖动；**必须先确认前台窗口是我们的**再拖，否则拖的是
别的窗口 —— 加 `foreground before drag: ours/NOT ours` + 回读 rect 才算数）、
`capwin.exe`（抓屏方法无效：BitBlt 抓 GPU 合成窗口得纯白，"拖动中 0 像素差异"是假象；
**先做对照组**这条教训救了一次错误结论）、`winmsg raw`（伪造消息能 30 秒验证子类化是否进了消息链）。

已全部写进 AGENTS.md「拖动窗口 / 改窗口大小」一节（含"看 qpc 跳变别数行数"的教训）。

## 拖动卡顿修复 + 整块玻璃/材质方案 + Vista 成本调查

**拖动卡顿**（用户："拖动窗口和 resize 会很卡"）：真因是喂进去的每帧都把模态循环堵住整帧，

EXITSIZEMOVE** —— 松手消息落在我们服务的那帧里被 SDL 泵吃掉，没这个收尾会留下
"定时器永远跑 + vsync 一直关"）。实测拖 2.1s/280px → 63 帧（≈30fps）、EXITSIZEMOVE 正常到达。

## 查证「整块玻璃」是否官方做法（结论：是，且我上轮写错了实现路径）

用户问"以这种方式实现整块玻璃是官方的做法吗"。查 MS 文档后的答案：

1. **负 margin 变玻璃是官方**：`DwmExtendFrameIntoClientArea` 的 Remarks 原话 ——
   "Use negative margin values to create the 'sheet of glass' effect where **the client area** is
   rendered as a solid surface with no window border"，示例函数就叫 `ExtendIntoClientAll`。
   所以我们现在做的（margins = -1）就是官方写法，**但它只管客户区** —— 这正是 Win7 上还能看见
   窗框内边框的原因。
2. **去掉非客户区也是官方**：`Custom Window Frame Using DWM` 这篇文档（不是社区博客）给了完整配方：
   `WM_NCCALCSIZE`（wParam=TRUE）**返回 0** → "the entire window region as the client area,
   removing the standard frame"；补 `SetWindowPos(..., SWP_FRAMECHANGED)` 让创建期就生效；
   然后 "the loss of the default resizing and moving behavior" 要自己用 `WM_NCHITTEST` 补回来，
   **附录 C 直接给了 `HitTestNCA()` 源码**；caption 按钮先交给 `DwmDefWindowProc`。
3. **我上轮的错**：写的是 `WS_POPUP` + 自绘 hit-test —— 那是社区做法。官方路径**不改窗口风格**

## "GL3.1 性能会不会比 3.3 好" —— 实测答：不会

GL 版本号是能力集不是性能档。我们本来就在 **3.3 core profile**（`SDL_GL_CONTEXT_PROFILE_CORE`），
core 是这附近唯一真正影响性能的开关。实测（关垂直同步、上限 240）：**1280x720 → 214 fps、
1920x1080 → 219 fps** —— 像素翻倍帧率不动 ⇒ 瓶颈在 CPU 侧（每帧提交/绘制调用），**不在填充率、
也不在 GL 特性**。降到 3.1 只丢功能（sampler object / 显式 attrib location；我们的 shader 其实
没用 `layout(location=)`，ImGui 后端自带 pre-3.3 分支），代码还得改一遍，换 0 fps。
已写进 AGENTS.md 的 Vista 那一节。

## Win7 切「自绘无框」崩溃 —— 根因是 WM_SIZE 被当成拖动消息喂帧（已修）

他实测：模式 1（DWM NCR off）→ Win7 回退 Basic 窗框，丑，**该档已删**；模式 2（自绘无框）→
效果出现约一秒后 AV 崩（c0000005，偏移 0x1d7812），**重启后带着该设置进来一切正常**。
只有运行时切换崩 ⇒ bug 在切换路径上。

**根因**（细节全在 AGENTS.md「玻璃实现」那节的「喂帧的教训」）：拖动喂帧那套把 `WM_MOVE` /
`WM_SIZE` 也当"拖动消息"喂帧，而 `depth` 只挡得住"我们喂出来的帧"里再嵌套 —— 普通主循环里
`depth` 就是 0。于是：设置卡片改设置 → `SetWindowPos(SWP_FRAMECHANGED)` → 客户区尺寸变化 →
`WM_SIZE` 同步到达子类 → **从帧体内部又跑了一整遍帧体**（含 `ImGui::NewFrame()`）→ ImGui 不可
重入。Win11 上侥幸活（实测嵌套 2~3 帧没死，所以本机复现不出来），Win7 上 AV。**为什么只有模式 2
会崩**：只有它改变客户区尺寸（±16x40），切 0↔1 尺寸不变、根本不发 `WM_SIZE`。

修法两道：① 子类加 `dragging` 门闩（只在 ENTER~EXITSIZEMOVE/按键松开看门狗之间喂帧）+ 把
`WM_MOVE`/`WM_SIZE` 从喂帧名单删掉；② 窗口结构变更投递到**帧边界**执行（卡片只置请求）。
回归：真拖动 54 帧、位移 240px；真缩放 34 帧、+160px —— 喂帧没被挡。切换探针连跑不再崩。

**排查手段（新增，以后 Win7 出问题都靠这三样）**：
- `SetUnhandledExceptionFilter` 崩溃处理器 → exe 旁 `cppsekai-crash.log`（异常码、出错地址 RVA、
  state/glassMode/frameless/frames、32 层返回地址）。Windows 子系统程序崩了什么都不留。
- 子类会把**非拖动期间**收到的 `WM_MOVE/WM_SIZE/WM_NCCALCSIZE/WM_WINDOWPOSCHANGED` 打出来并
  标 `- not served`（Win11 实测切换时三个都来，Win7 同样）—— 一眼看出有没有再嵌套。
- `CPSEKAI_GLASS_TOGGLE=<秒>` 探针：自动翻一次玻璃实现，走卡片同一条投递路径，不用手点就能复现。

**记住这条死路**：zig 的 lld **不往 exe 写 COFF 符号表**（`ptrsym=0 nsyms=0`；`-g`、
`--export-all-symbols` 都没用；`-Wl,-Map` / `/MAP` 被 zig 直接拒），所以「拿崩溃偏移查函数名」
在这套工具链上做不到 —— 我为此白做了一轮（还写了 pe_symbols.py，已删）。定位只能靠崩溃日志 +
步进日志 + 探针。

## 「切换渲染质量提升性能」可行性实测（18:50~19:00）—— 结论：这台机器瓶颈不在渲染

起因：用户问能否加渲染质量档。做法是**先量再说**：临时在帧率采样块加了一个环境变量探针
（`CPSEKAI_FRAME_LOG=1` 时每秒无条件打印 fps + render 尺寸），测完已经精确撤掉、重编过，
main.cpp 回到干净状态（`grep TEMP PROBE` = 0，`git status` 干净）。

测法：`--instance multi --no-party --auto --fps 1000 --window borderless --width 1920 --height 1080
--render-size <WxH> --screenshot ... --screenshot-time 12`。
关键点：`--fps 1000` 超过刷新率 → 代码自动关 vsync，才能测出真实上限；`--screenshot` 全程不写存档。

| 场景（窗口恒 1920x1080，autoplay，无上限） | 渲染 1920x1080 | 渲染 960x540 |
|---|---|---|
| test.sus（20 音符） | 947–991 fps | 952–993 fps |
| 0001_master（12 s，72 音符） | 965–987 fps | 966–991 fps |

→ 1080p 帧时间约 **1.0 ms**，540p 约 **1.01 ms**：**降分辨率几乎换不来帧率**。这台机器上帧时间
的大头在 CPU 侧（谱面核心 + ImGui 组装 + 音频 + swap），填充率不是瓶颈。60 fps 的预算是 16.6 ms，
现在只用掉 1 ms。要真看出填充率的斜率，得换成弱 GPU（VM 软件渲染 / 老核显 / Win7 老机器）。

**两个坑（下次别踩）**：
1. **Git Bash 不等 GUI 子系统 exe**：`for r in ...; do ./cppsekai.exe ...; done` 会几乎同时
   启动多个实例，互相抢 GPU —— 第一轮测出的「1080p 只有 245 fps」就是这个假象。串行必须
   写成 `./cppsekai.exe ... & sleep 20`，再 grep 日志。
2. **日志落在 cwd 的 `cppsekai.log`，不是 `build/` 那份**（那次读的是用户自己从 build/ 跑的）。
   从仓库根跑就要去根目录捞，而且每次运行会覆盖它。

实现侧结论（若以后要做）：离屏管线已经现成 —— `Renderer::setRenderTargetSize(w,h)` +
`presentFrame()` 的等比放大 + letterbox 就是内部分辨率缩放要的全部机制，只要允许
「渲染尺寸 = 窗口尺寸 × 百分比」，宽高比一致时放大正好铺满、零黑边。约 30~40 行（设置字段 +
applyRenderMode + 画面页下拉）。**是否值得做由用户拍板**（当前机器收益 ≈ 0）。

## 内存审计：「壁纸背景吃 50MB」证伪 + 180MB 的构成（19:00~19:20）

用户报告：背景填充选桌面壁纸时启动 ~230MB，切回默认渐变降到 ~180MB，再切回壁纸却不涨。

### 结论：三个观察，三个互不相关的原因

| 观察 | 真相 | 证据 |
|---|---|---|
| 壁纸比渐变"多 50MB" | **壁纸只值 2.2MB**（一张 1024x575 RGBA8 纹理） | 两种 bgStyle 各跑一次：稳态 251.5 vs 249.3 MB |
| 切回渐变掉 50MB | **启动期临时分配的延迟归还**，跟背景设置完全无关 | bgStyle=0 也有同一个台阶，且固定在启动后 **10.5~12 s**；峰值 291.6 → 稳态 245.4 |
| 切回壁纸不再涨 | **代码里就是缓存**：`backdropKey = path + "|" + blur`，`if (key != backdropKey)` 才重载 | main.cpp:2063；切到非 1 时直接 return，连纹理都不删 |

### 内存构成（实测，1280x720 窗口、选曲界面）

- **GL 空窗口基线 72 MB** —— 单独编了个只有 SDL2 + GL 3.3 context 的最小程序对比（见下）
- **字体 TTF 数据常驻 ~36.7 MB ← 真正的大头**：`msyh.ttc` 19.7 MB + `msyhbd.ttc` 16.9 MB +
  `ARIALNB.TTF`。新版 ImGui（1.92 动态字体纹理）按需光栅化，**但要求整个 ttf 常驻内存**，
  换来的好处是 atlas 只有 512x128 = **0.25 MB**（实测打印）。这是架构代价，不是泄漏。
- 游戏贴图 ~13.5 MB（`CPSEKAI_TEX_RAW=0` 对照：251.5 → 238.0）
- 谱面列表 + preview 音频 + 缩略图 ~3.3 MB（`--charts <空目录>` 对照）
- 壁纸纹理 2.2 MB

启动曲线（150ms 粒度，`GetProcessMemoryInfo`）：0.15s **74** → 0.30s **145** → 0.60s **197**
→ 0.75s **276**（← 字体那一步 +79MB）→ 峰值 **291.6** → 12 s 后 **245.4**。
→ 峰值比稳态高 46MB，全在 `[boot] fonts`（12 个系统字体候选逐个试，字体文件是整读进内存的）。

### 顺手得到的两个可做项（用户没让改，记着）

1. **字体**：`msyhbd.ttc` 那 16.9 MB 只为粗体；`AddFontFromFileTTF` 对每个 font 都持有一份
   完整文件数据，同文件多 font 不会共享。想省就得 `ImFontConfig::FontData` +
   `FontDataOwnedByAtlas=false` 共用一份 buffer，或者砍掉粗体。
2. **大壁纸的解码峰值隐患**：`loadBackdropTexture` 是**先全尺寸 `stbi_load` 再缩到 1024**，
   stb 不支持解码时降采样。现在这张 2489x1400（13.3MB RGBA）无所谓，但用户换一张
   8K 全景壁纸就是几百 MB 的瞬时分配。要防就先 `stbi_info` 探尺寸、超阈值直接回退渐变，
   或换 WIC 的 `IWICBitmapSourceTransform`。
   （`CachedFiles\CachedImage_*_POS4.jpg` 那条路不值得走：同一张图的 1920x1080 版只省 5MB 解码，
   还多一个"文件名跟分辨率绑定"的依赖。）

### 关键发现：ImGui 画不出空心字，必须自己做轮廓纹理

旧的 `textOutlined()` = 12 层圆周偏移的实心字（白 α56）+ 一层 `bgColorAt()` 硬编码渐变
（46,47,74 → 74,62,124）挖空。**挖空色必须等于背景色**才看不出 fill，而背景是**带图案的**
`background_overlay.png`（x 方向 `#011049` / `#3f3c5a` / `#1b193d` 乱跳），任何近似色都会
露出色块（中间态截图就是这样）。ImGui 的 draw list 只能盖**实心**字形，blend 又没有"擦除到
透明"这种操作（帧缓冲里已经是最终颜色了），所以**字形本身就必须是空的**。

→ 新增 **`platform/FontOutline.{hpp,cpp}`**：
- 用 `third_party/imgui/imstb_truetype.h`，**必须 `#define STBTT_STATIC`** ——
  imgui_draw.cpp 里已经编进了一份实现（非 static），不加就会链接冲突。
- 光栅化 → **圆形膨胀 − 原覆盖** = 环（逐像素相减，抗锯齿边缘保持平滑）→ RGBA8。

## chartdl 六项改动（20:00~20:40）

### 1. 真 bug：关掉设置窗口后整个下载器点不动 —— 根因已实测

`settingsProc` 的 `WM_DESTROY` 用 `GetParent(hwnd)` 找主窗口，好恢复 `EnableWindow`。
**但设置窗口是 `WS_OVERLAPPED` 的*顶层*窗口，CreateWindowExW 第 8 个参数给的是 owner 而不是
parent，而 `GetParent()` 对 owner 返回 0。** 实测（Python + ctypes 建同样的窗口）：

```
parent    = 0x530730        <- CreateWindowExW 传的
settings  = 0x250ba0
GetParent (chartdl 原来用的) = 0x0        <- 所以那句 if 永远是假
GetWindow(GW_OWNER)          = 0x530730   <- 这个才对
```

于是 `EnableWindow(parent, TRUE)` **一次都没执行过**，主窗口永久禁用 —— 点什么都只有系统
提示音。**改成 `GetWindow(hwnd, GW_OWNER)`。**

验证手法（可复用）：`chartdl.exe --open-settings` 起 GUI，Python ctypes 按类名找窗口
（主 `CppSekaiChartDl` / 设置 `CppSekaiChartDlSettings`），`PostMessage(WM_CLOSE)` 给设置窗口，
前后读 `IsWindowEnabled(主窗口)`：**0 → 1** ✓（修复前会永远停在 0）。

`GetParent(gList)` 那几处**不要动** —— ListView 是真子控件，GetParent 对它是对的。

### 2~6. 其余五项

- **队列清空**：点「开始下载」先 `gJobs.clear()` + 进度条归零。原来只是追加，旧条目已经
  Done 还在 `gJobs` 里参与统计，所以「xx/xx 个文件」和进度条都从旧总数起算。
- **进度条不再虚高**：改成**按文件数** =（已完成 + 正在下载那几个文件的字节比例）/ 总文件数。
  原来按字节算，而入队时每个 job 的 `total` 还是 0（Content-Length 要等响应头才拿到），
  分母小得可怜 → 还没开始下就 100%。
- **剩余时间**：用同一个 fraction 推（`elapsed / fraction * (1 - fraction)`），指数平滑 0.25，
  状态栏「剩余 1 分 23 秒」。和进度条同源，两者不会互相矛盾。
- **多线程**：`kDownloadThreads = 4`。worker 本来就是「取一个 Waiting job 就下」的模式，
  直接多开即可，但两个配套必须做：① `gRunning` 原来**每个**线程结束都置 false，多线程下会
  提前报"全部完成"，改成 `gActiveWorkers.fetch_sub(1) <= 1` 才算完；
  ② **`http::get()` 把 WinHTTP session + connection 缓存在 `thread_local` 里**，不再每个文件
  `WinHttpOpen` + 重新握手。连接被服务器半关时由 worker 重试一次（丢缓存连接 + 截断 .part
  重下；`HTTP xxx` 状态码不重试，那是最终答案）。
- **ID 列宽**：48 → 64。

## autoplay 会 miss —— 判定引擎的真 bug（20:45~21:10）

用户报：`--auto` 跑「いますぐ輪廻」MASTER，`[stats]` 里 **miss=22**（自动演示本该零 miss）。
**这条同时解释了"手打时莫名断连"**：这些音符根本不接受输入。

### 定位手法（可复用）

1. **探针**：`registerMiss()` 里打印"刚变成 state 2"的音符（kind / center / width / flags /
   holdTail）。要点：用 `std::set<float>` 按时间戳去重 —— 同一个音符在随后几帧还会落进
   搜索窗口，不去重会刷屏。
2. **事件表对照**：`--dump-events 3000` 导出全部 packed HitEvent，Python 按时间配对。
   （`--dump-events` 的格式是 `[events] N total, first n:` + `  #i t=… kind=…`；
   日志里另外那种 `hitEvent[i]` 是 main.cpp 另一处的输出，别混。）
3. 结论：**22 个 miss 全是 `holdTail=1`**，且 great/good/bad 全 0 → 它们**没走输入判定**。

### 根因（两层，都要修）

**第一层：尾判被当成独立音符判了 MISS。**
`update()` 的 holdTail 分支原本"仍然 pending 就 `registerMiss`"。但长条的尾巴是**靠松手结算**的
（hold 跟踪里判 Perfect/Great/Good），起点没抓住时**起点的 MISS 已经算过整条** —— 这里等于
**重复扣分**。原注释写"the hold never started at all"，可那种情况早就被另一条路径
（`startState == 2` → 静默消费）处理掉了，注释是错的。

**第二层：为什么会有尾判没人认领。**
`spawn` 给 hold 挑 tail 用的是「**距 hold 起点 lane 最近**」，而**滑动长条的尾判事件在终点 lane**。
实测 `t=5.897`：两条 HOLD（起点 center 1.00 / -4.00，同一 tick 结束）配两个 HoldEnd
（-0.50 / 4.50），两条 hold **都抢 -0.50**，4.50 永远 pending → 落到第一层的 MISS 路径。
（另有 31/66 个 hold"找不到 tail"，那是 0.052 秒的极短 hold，正常。）

### 修复

1. `mTailClaimed`（Judgement.hpp 新成员，load/reset 里 assign 0）：**一个尾判只能被一条 hold 认领**，
   认领后其它 hold 跳过。
2. holdTail 分支改成**静默消费**（`note.state = 2`，不 `registerMiss`）：语义正确 —— 它本来就由
   hold 结算，没有 hold 认领意味着起点已 miss 或它是游离事件，不该二次扣分。

### 实测

| 版本 | miss | maxCombo | 结束血量 |
|---|---|---|---|
| 原版 | 22 | 140 | 3240 (64.8%) |
| 只加认领唯一性 | 21 | 140 | — |
| **认领 + 静默消费** | **0** | **890**（全程不断） | **5000 (100%)** |

**教训**：`--auto` 的 `[stats]` 行是判定引擎的黄金基线（"自动演示应当全 PERFECT、0 miss"），
任何判定改动都先跑它。

用户要求：在「下载内容」下面加一个显示所有别名的分组框，两者之间加拖拽手柄。

- **别名面板**：**一行一首「有别名的」曲目**（`#123 曲名`，按 id 升序和左边主列表同序），
  **选中一项 → 下面的只读多行框显示该曲的别名**。我用 LVS_OWNERDATA 虚拟列表，
  行数据 `{id, 显示串, 别名串}` 在 `rebuildAliasRows()` 里一次拼好，选中时直接塞进编辑框。
  第一版把索引平铺成「别名 → 曲目」是**理解错了用户的意思**，返工过一次 —— 他要的是
  「列表列曲目，选中看别名」。
- **换行得手工算**：那个只读 EDIT **不会软换行**（它长出了水平滚动条），而一个别名一行又
  太浪费（`hs` / `kz`）。按 UTF-8 字节数约 54 一行、别名之间用「、」。
- **第三条分隔条**：右侧面板被 `gDetailHeight` 切成上下两块。复用既有那套：
  `splitterRects()` 多返回一个矩形 → `hitSplitter()` 多返回 3 → `WM_MOUSEMOVE` 里
  `gDetailHeight = gDragStart + deltaY`（和底部那条**方向相反**，向下拖是变高）。
  顺手让 `hitSplitter()` 真的去调 `splitterRects()` —— 它以前是死代码，注释却写着
  「几何只有一处，改一个不会让另一个失配」，名不副实。
- 坑：`splitterRects` 里 `client.right` 是 `LONG`，和 `dp()` 的 `int` 一起进 `std::max`
  **推导不出模板**（编译错误），显式 cast 才过。
- **无头驱动 chartdl 的可用手法**（这次摸出来的）：`SetForegroundWindow` + `BringWindowToTop`
  之后，用 `SetCursorPos` + `mouse_event` 发**真实**点击是有效的；坐标按 `layoutChildren`
  的公式从 `GetClientRect` 反算（`dp(x)` 在 dpi 96 下就是 x，直接照抄 C++ 那几行）。
  `--screenshot-time` 留够（20s）让点击发生在截图之前。

### 四个真病根（带代码位置）

1. **字体 100MB —— 最大单项，两个独立原因**
   - `game/Intro.cpp:545` 和 `:562` 对**同一个** `msyh.ttc` 调 `AddFontFromFileTTF`
     两次（Japanese ranges + MergeMode 简中 ranges）。ImGui 每次
     `ImFileLoadToMemory` 一份完整文件且 `FontDataOwnedByAtlas` 默认 true
     （`imgui_draw.cpp:3148`）→ **19.7MB × 2 = 39.4MB 常驻**，两次调用之间不共享。
   - `Intro.cpp:440-441` / `541-542` 硬写 `OversampleH=2; OversampleV=2`。
     1.92 的 auto 规则是 `raster_size > 36 ? 1 : 2`（`imgui_draw.cpp:3407`），
     本项目字体 42px > 36 → **auto 本来就是 1**；`ImGui.h:3658` 还明说
     OversampleV「Y 轴不用 sub-pixel，没什么用」（auto=1）。
     等于每个字形位图面积是必要的 **4 倍**（84×84 vs 42×42）。
   - 对照实验：`CPSEKAI_FONT_FILE=<msyh.ttc>` 跳过 12 个候选探测，字体那步仍 +103MB
     （所以候选探测不是主因），但稳态只从 282.6 → 274.0（被拒的方正兰亭圆只多占 8.6MB）。

2. **谱面封面 740×740 全尺寸上传 + static 缓存永不释放**
   `SongSelect.cpp:1918` `thumbFor()` 的 `static std::map<std::string, GLuint> cache`
   只增不减；`Renderer::loadUiTexture` → `loadTextureFromFile(path, err)` 不传 maxDim
   → 原尺寸。charts 里 29 张 png 全是 740×740 = **2.09MB/张，全滚一遍 60.6MB**，
   而列表里画出来只有 ~100px。**这是唯一"用越久越高"的项。**

3. **教学 UI 三张 1920×1080 全屏 RGBA**
   `StoryUi.cpp:160-167`（Dialogue / Choices / SceneText_Background）。全目录 12 张
   全是 1920×1080=7.9MB（vignette-round 2340×1080=9.6MB），加载 3 张 = 23.7MB
   + 解码峰值 → 实测该步 +49.8MB。纯渐变/暗角，降到 1/4 无可见损失。
   `build/assets/story/ui/` 整目录 98.9 MB 解码体积。

4. 场景贴图 48 / HUD 31 —— **不建议动**：09-19 踩过"降采样后精灵矩形错位"

### 1. 字体 oversample（`game/Intro.cpp`）

（`imgui_draw.cpp:3407`），42px 本来就选 1；`ImGui.h:3658` 说 OversampleV 在 Y 轴没用。

### 2. 字体只读一份 TTF ⚠ 报告里的方案是错的

原方案「`AddFontFromMemoryTTF` + `FontDataOwnedByAtlas=false` 共享 buffer」**走不通**：
`AddFont` 里 `FontDataOwnedByAtlas == false` 会先 `ImMemdup` **复制一份**再把所有权设回
true（`imgui_draw.cpp:3059`），传 false 只会多复制一次。

正解：`mergedBodyRanges()` 把 Japanese + 简中 ranges **排序去重并成一个数组**，只调一次
`AddFontFromFileTTF`。字形集是同一个并集。省 19.7 MB。
（`RemoveFont` 能清掉被拒候选，但对照实验显示它稳态只占 8.6 MB，不值得冒险，没做。）

### 两个解析坑（都会让结论完全跑偏）
1. **Unity Gradient 的 key 数组**：只有前 `m_NumColorKeys` 个的 RGB 是颜色（ctime 轴），

2. **颜色是线性空间**：`(0.138,0.175,0.302)` 直接当 sRGB 用是近黑，必须过 sRGB 转换。

## 触摸特效第五轮：继续缩小 + hold 去环 + 三角形 3D 化

用户第四轮反馈三条，都对：

1. **继续整体缩小** → `kRingScale` 0.60 → **0.45**（环 160→72）。
2. **hold 状态没有青绿色圆环** —— `Follow` 里的 `PT_01`（330，looping 1）**`rateOverTime = 0`**，
   Unity 不会自动发射，只能靠代码 `Play()`，而游戏没播它。所以按住时只有
   **650px 白色光晕 + 环绕的三角**。代码里已删掉 hold 的环和 `kHoldRing/kHoldRingLife`
   两个常量（留着会有 unused 警告，项目要求 0 警告）。
3. **三角形是 3D 的** —— 关键在 `RotationModule.separateAxes = 0`：
   **只有 Z 轴在转**（π rad/s），X/Y 不转，但 `startRotation` 是 Vector3（三轴各自 ±2π），
   所以**每颗三角有固定随机倾角**。渲染必须做真 3D 投影（绕 X→Y→Z，正交投到 XY），
   倾斜的 quad 会压扁成瘦长条 —— 这才是"翻滚玻璃片"。纯 2D 旋转（绕 Z）做不出来。
   `mat_sekai_01_2` 的 `_Cull: 2` 是双面，所以背面也画。

### 缩放拆成两个（都非实测）
- `kRingScale = 0.45`：环 + 光晕 + 发射半径
- `kShardScale = 0.60`：三角直径
- **为什么拆**：环缩到 0.45 好看，但三角跟着缩就成微粒（24px 再被 3D 压扁），
  用户上一轮才说过"小成微粒"。所以三角单独一档。

## 过曝（教程/选曲泛白）—— 根因确认，不是「修好了」

昨天 `e690519`（提交信息就叫 "1"）在 `presentFrame()` 后、`swap` 前补了一遍
`glColorMask(0,0,0,1) + glClear(alpha=1)`，并留了 `veil_1..4.png` 对比图
（veil_1 泛白 / veil_2 正常，**连卡片本身都一起变亮** = 整帧和浅色桌面混合的特征）。

今天加日志量出关键一条：

```
[gl] framebuffer alpha=0 (asked 8) depth=0 maxTexture=16384   ← 开发机 Iris Xe
```

`SDL_GL_ALPHA_SIZE=8` 只是**请求**，WGL 给不给看驱动像素格式。开发机是 0 →
`glClearColor(...,0)` 的 alpha 被丢弃 → DWM 拿到不透明画面 → **过曝物理上不可能
出现**，跟改了什么代码无关。所以「这台机器奇迹般消失」= 两台机器跑的不是同一条
合成路径。副作用推论：**开发机上「玻璃背景」大概也是无效的**（静默降级成不透明）。

根因是窗口一直在 `DwmExtendFrameIntoClientArea(-1,-1,-1,-1)` 下（本来只服务
splash 和玻璃背景），任何 alpha<1 的像素都会和桌面混合。
**截图永远看不出来**：`--screenshot` 读的是 GL buffer，alpha 不进 PNG。

## TDR（演奏中白条 + 卡住 + 整屏黑一下）

「屏幕黑一下再恢复」在 Windows 上基本只能是驱动超时重置。判据：
`wevtutil qe System /q:"*[System[(EventID=4101 or EventID=4102)]]" /c:10 /rd:true /f:text`

给 `Renderer::renderFrame` 加了提交前体检 `quadIsGarbage()`（`platform/Renderer.cpp`）：

- **坑（第一版写错，记下来）**：阈值取 256，每帧误杀 2~8 个特效 quad。
  effect 的 x/y 是**除以 w 之后的 clip 坐标**、`1/w` 单独存在 rw 里（shader 乘回去），
  摄像机后方的顶点会合法地打包成 `x=430, 1/w=-33`。所以判据必须 `x/rw` 还原后再看量级，
  而且**负的 1/w 是合法的**。改成 1e5 + 非有限值之后三场景 0 误杀。
- 实测结论：**正常演奏的数据是干净的**（`--auto` 30s / 选曲 / 结算都 0 dropped），
  白条不是每局都埋着的雷，要等出事那台机器的日志。
- 探针（出事才出声）：`[gl] dropped N garbage quad(s)` /
  `[gl] slow swap XXX ms (present waited on the GPU)` / `[gl] context lost`。
  `slow swap` 比 Windows 复位更早，是最便宜的 GPU 侧探针。
- `CPSEKAI_GL_TRACE=1` 才打印坏 quad 的原始 25 个 float。

## 补（22:45）：veil 图全是正常的，真 bug 在开关逻辑

用户说 `veil_1..4.png` **全是正常画面**（差别只是模态遮罩淡入到第几帧），
出问题那一刻从来没截到。所以上一轮「veil_1 是泛白版」的解读是错的，
已把 GPU-GLITCH.md 改掉 —— 结论改成从**开关时序**推出来，不依赖复现。

顺着这条线翻出一个真 bug（不是 alpha 补得不够）：

1. `main.cpp` 2379 启动时 `if (splashStyle == 0 || glassBackground) applyGlassWindowMode(true)`，
   但 **splash 结束时只恢复了边框/全屏，从来没调用过 `false`**。`splashStyle` 默认
   就是 0 → 默认配置下整局（选曲 + 打歌）都跑在 DWM 逐像素合成下。
2. 设置卡 4799 用的是 `requestGlassWindowMode(splashStyle == 0 || bgStyle == 2)`，
   `splashStyle == 0` 在运行期**恒为真** → 每次切背景都重新打开透明，
   **连「从玻璃切回不玻璃」也会打开**。这条最容易撞：动一下背景设置，画面当场泛白。

修法（commit `39b66b4`）：
- splash 结束、且 `!glassBackground` → `applyGlassWindowMode(false)` 收回扩展帧；
- 4799 去掉 `splashStyle == 0 ||`，只按 `bgStyle == 2`。

验证：`[window] ... per-pixel alpha on`（splash）→ `off`（加载完），
演奏截图正常、0 dropped / 0 slow swap。日志文案顺手加了 transparency 状态。

**注意**：`applyGlassWindowMode` 定义在 `#ifdef _WIN32` 里，2879 那处调用必须
自己包 `#ifdef`（splash 结束块在 Windows 条件之外）。

## 「平台串线」的答案：绘制不串，窗口串

- **绘制**：`aeroGlassAvailable()` 用 RtlGetVersion 严格判 `major==6 && minor<=1`。
  Win10 返回 false → 背景列表只剩 2 项（玻璃项不出现）、存档里 `bgStyle==2` 被改写成 1
  并打 `[bg] Aero glass is not available on this system`、`glassMode` 钉成 0。
- **窗口**：`DwmExtendFrameIntoClientArea` 是 Win7+ 通用 API，Win10 上照样把一个普通窗口
  变成逐像素合成 —— 原来「splash 开场后不收回」那段在 Win10 上一样跑（今天修掉的）。
  所以「Win10 碰到毛玻璃相关代码」的感觉是对的，但碰到的是玻璃的**窗口前提**，不是画法。

## 踩坑：重定向 stdout 会让日志不落盘
- `( cppsekai.exe ... >/dev/null 2>&1 & )` 之后 **`cppsekai.log` 不会生成** —— main.cpp
  检测到 stdout 已经被重定向就继续写 stdout（`main.cpp:857` 那段），于是日志全进了 /dev/null。
- 无头跑要看日志时**别重定向**（`( exe ... & )` 或 `( exe ... & wait )`），或者用 `--screenshot`
  让它自己退，然后在 cwd 读 `cppsekai.log`。

## 第四轮：代码体检复检（CODE-REVIEW.md 更新）
- 量法：Python 脚本按括号配平找「同层级最长花括号块」量函数体 —— **`namespace {`、
  `if (tab == N) {`、`} else if (...) {` 都会误报成巨型函数，必须按行号回查**。
  扫描脚本用完即删，别在仓库留探针。
- 结论：**唯一在恶化的是 `main()`（5,713→6,641）和 `drawSongSelect()`（1,746→1,920）**。
  三天原创代码 23,840→27,233（+3,393），但 `chartdl.cpp`(+852) / `Ui.cpp`(+460) 都是
  **加函数**涨的 —— 除这两个巨型函数外，**全项目最大单函数只有 205 行**。
  行号：`main()` 849-7489；`runFrame` lambda 4476-7206（自带 `// end runFrame` 注释）；
  `drawSettingsCard` 2987-3861；`drawSongSelect` SongSelect.cpp 2397-4324。
- **新发现**（旧版没有的）：
  1. **`chartdl.cpp` 有 4 处死声明**：`gPendingBalloon` + `gPendingMutex`（一对从未使用的
     托盘气泡功能，**mutex 声明了却从未上锁 —— 读代码的人会以为它是线程安全的**）、
     `gNeedClearTicks`、`gGuiStartSec`（注释写 `for --screenshot-time` 但从未读写）。
     零引用，可直接删。
  2. **`json.hpp` 存了两份**（`third_party/` 与 `core/native/vendor/`，md5 相同，
     nlohmann 3.12.0）。**不能直接删**：`mmw_preview.cpp:28` 用相对路径
     `"../vendor/nlohmann/json.hpp"` 钉住了 vendor 那份（上游代码，AGENTS.md 说不改结构）。
     真风险是**跨 TU 的静默 ODR** —— 只要将来只升其中一份，就是 UB 且**不报错**
     （nlohmann 的版本检查只在单 TU 内 `#warning`）。最小修法：vendor 那份换成一行转发头。
  3. **「baseDir → .. → cwd」三级候选路径手写了 7 遍**（4 处 json + icon.png + charts +
     chartdl.exe），~45 行可压成 1 个 `findDataFile()`。
  4. **调试探针转正后散在生产路径**：`getenv` 全项目 16 处（main.cpp 9），
     `CPSEKAI_UI_TRACE` 一个就在 main.cpp 出现 5 次。虽有价值（无头验证靠它）但该收敛。
  5. **没有任何 `-Wall`**（`build.sh:16` 只有 `-std=c++20 -O2 -s`），但**代码本身是干净的**：
     `-Wall -Wextra -fsyntax-only` 实测 **15 个文件 0 警告（含 7,489 行的 main.cpp）**，
     只有 `chartdl.cpp` 23 个（11× `-Wcast-function-type-mismatch` + 8×
     `-Wmissing-field-initializers` 是 Win32 惯用噪音，4 个真的）、`SongSelect.cpp` 4 个。
     → 加 `-Wall -Wextra` 成本几乎为 0。

  `main.cpp` 内 static 44→55、`build.sh` SOURCES 仍手写 28 条（09-18 排第 1 位，一直没做）。

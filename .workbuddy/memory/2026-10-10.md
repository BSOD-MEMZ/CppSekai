# 2026-10-10

## 无显卡机器上的崩溃定位（0xC0000005 @ rva 0xDA3E7）

用户在一台没有 GPU 驱动的机器上跑 `CppSekai-2026-09-30`，给了两份日志
（`D:\Downloads\cppsekai.log` / `cppsekai-crash.log`）。**只做了定位与结论，未改代码**（用户只问了问题）。

### 结论
崩溃**不是有意为之**，是「GL 3.3 拿不到」这条失败路径没接住；但「要求 GL 3.3」是有意的
（AGENTS.md 1239 / 1795 已记）。

### 完整证据链（以后同类问题照这个走）
1. 日志只有 `Failed to initialize OpenGL loader!` —— 出自
   `third_party/imgui/imgui_impl_opengl3.cpp:303`（`ImGui_ImplOpenGL3_InitLoader`）。
   该分支要求 `imgl3wInit() != 0`，而 loader 的 `parse_version()` 只在 **major < 2** 时返回错
   （`imgui_impl_opengl3_loader.h:833`）。⇒ 拿到的上下文是 **OpenGL 1.1**（Windows 无 3D 驱动时
   opengl32.dll 的 GDI Generic 软回退），不是"缺函数指针"。
2. **`SDL_GL_CreateContext` 居然成功了**：日志里有 `[boot] gl context 95.3 ms`（main.cpp:2133），
   所以 main.cpp:2126 那条 `OpenGL 3.3 core unavailable` + `return 1` 的守卫**没触发**。
   ⇒ 现在的守卫挡不住"拿到上下文但版本不够"这种情况。
3. `ImGui_ImplOpenGL3_Init()` 返回 false（main.cpp:2198 **没接返回值**），
   `io.BackendRendererUserData` 一直是 NULL。
4. `drawSplash()`（main.cpp:2233）→ `ImGui_ImplOpenGL3_NewFrame()` →
   `bd = ImGui_ImplOpenGL3_GetBackendData()` = NULL → `if (!bd->ShaderHandle)` 读 `[NULL+0x30]`
   → **0xC0000005**。崩溃 rva 0xDA3E7 的指令就是 `83 7E 30 00` = `cmp dword [rsi+0x30],0`。
5. `frames=0` ⇒ 还没进主循环（`gCrashFrameCount` 只在 main.cpp:6216 自增），和上面吻合。

### 定位手法（可复用，写进 skill 了）
- `.pdata` 反查函数边界：崩溃点落在 **0xDA380..0xDA3FF（127 字节）**，正是
  `ImGui_ImplOpenGL3_NewFrame()`（`ShaderHandle` 在 `ImGui_ImplOpenGL3_Data` 偏移 0x30）。
- **字符串交叉引用**比硬扛汇编快得多：扫 `.text` 里 `48/4C 8D|8B <modrm.rip>` 的 disp32，
  算 `insn_end+disp` 是否命中目标串 RVA。
  - `"imgui_impl_opengl3"`（BackendRendererName）→ rva 0x49BD70，被 0x0xD9F9A 引用 → Init 所在函数；
  - `"Failed to initialize OpenGL loader!"` → rva 0x49BD44，**4 处**引用（InitLoader 被内联进 4 个调用者）。
- **IM_ASSERT 在发布版是编译掉的**：二进制里搜不到
  `"Context or backend not initialized"` / `"Already initialized a renderer backend"`，
  所以那句本该拦住 NULL bd 的断言没响。手工 hex 装 capstone 失败（无网络），靠 `.pdata` + 交叉引用够用。

### 顺带发现（真 bug，未修）
`cppsekai.log` 被 `freopen(..., "w", stdout/stderr)` **打开了两次**（main.cpp:~1107 和 ~1484），
两个 FILE* 写同一个文件 → 用户日志第 2 行那个 ` uses DPI scaled points)` 碎片就是这么来的
（前 36 字节被第二次打开的 stderr 覆盖，正好是 `"Failed to initialize OpenGL loader!\n"` 的长度）。
副作用：**崩溃前的 stdout 缓冲会丢**，所以"日志最后一行 = 崩溃阶段"不可靠。

### 给用户的答复要点
- 能不能硬跑：只看「有没有 GL 3.3 的驱动」，不看有没有独显。集显（Intel HD / AMD APU，2010 后）能跑；
  只有「Microsoft 基本显示适配器」/ RDP 会话 / VM 没开 3D / 驱动只到 GL 1.1~3.1（AGENTS 里 Vista+Intel 集显）→ 不行。
- 硬办法：把 **Mesa3D 的 64 位 `opengl32.dll`（llvmpipe 软光栅）** 放到 exe 同目录，
  让程序用纯 CPU 的 GL 4.5 跑起来；代价是慢，配 `--render-size 960x540` 之类的小尺寸。
- 提了三个可选的代码改动（友好拒绝启动 / 补 GL 版本检查 / 修二次 freopen），等他点头。

# 第二轮（同日晚）：无显卡「硬上」代价实测 + 另一台 Win10 的 filesystem 报错

## Mesa 软件渲染实测（回答「学校机房云主机没显卡，硬上代价多大」）

- 做法：从 `pal1000/mesa-dist-win` 26.2.4 取 `mesa3d-26.2.4-release-msvc.7z`（70MB）；
  **bsdtar（`tar.exe`）报 `LZMA codec is unsupported`、py7zr 报 `BCJ2 filter is not supported`**，
  最后用官方独立命令行 `https://www.7-zip.org/a/7zr.exe`（600KB）解开 —— 这条以后直接用。
- **接管只需两个 DLL**：`x64/opengl32.dll`(139KB) + `x64/libgallium_wgl.dll`(61MB) 丢进 exe 目录，
  配 `GALLIUM_DRIVER=llvmpipe LIBGL_ALWAYS_SOFTWARE=1`（d3d10warp / va / clon12 那些都不需要）。
- 本机 i7-1260P（16 逻辑核）实测 @1366x768、`--fps 240`（=关垂直同步）：
  **选曲 55–66 fps**（longest 20–32ms）、**演奏 `--auto` 83–112 fps**（longest 14–23ms）。
  对照 AGENTS 里记的同机真显卡 214–219 fps → **软件渲染只慢 2–3.5 倍**，比预想便宜得多。
  代价的重头不是 fps，而是 CPU 被吃满 + 云桌面延迟（perfect 窗口 70ms，判定游戏基本没法玩）。
- **A/B 证明 Mesa 真被加载**：`MESA_GL_VERSION_OVERRIDE=1.1` → SDL 直接建不出上下文 →
  `OpenGL 3.3 core unavailable: Could not create context` exit=1；把两个 DLL 藏起来后同一命令正常跑到首帧。

## 测量方法的坑（重要，别再用错数字）

- `[frame] N frame(s)/s`（main.cpp:6246 起）**每秒重置，只在「窗口移动 >0.5px」或「该秒有 >60ms 帧」时打印**
  → 静止窗口只会给出「启动那一秒」，同一构建我拿到过 20 / 28 / 44 三个互相矛盾的数。
  正规做法： `.workbuddy/tools/window_nudge.py <秒> SDL_app` 每秒把窗口挪 2px，逼出每秒一条稳态采样。**新增文件，待 commit。**
- 进程被强杀后单实例锁会残留 → `[instance] already running (window not found)`，
  `profiles/` 下没有锁文件（疑似命名互斥体），重跑前多 taskkill 几次 + 等进程真的消失。

# 第三轮：定位并修掉（用户确认现场报的就是 `Illegal byte sequence`）

## 根因（只有一处）

`game/SongSelect.cpp` 的 `userDataDir()`：

```cpp
const fs::path file = userDataPath(exeDir);   // ← 就是这一行
```

`userDataPath()` 返回的是 **UTF-8 的 `std::string`**，隐式构造 `fs::path` 时 libc++ 用
**本地 ANSI 代码页**去解码它：

- cp936 上把目录名整个毁掉（`中文安装目录\子目录` → `涓枃瀹夎鐩綍` + 尾部的 `\` 被双字节字吃掉，
  于是 `parent_path()` 切在别处 —— 这就是上一轮"连取父目录/exe 目录都变了"的原因）；
- 字节不合法时直接抛 `filesystem_error: __char_to_wide: Illegal byte sequence`，
  没人接 → `std::terminate` → Windows 子系统下**没有任何反应**。

改成 `const fs::path file = toFsPath(userDataPath(exeDir));` 即可。

**为什么"Win11 的下载目录没事、Win10 的不行"**：Win11 那台大概率开了
「Beta: 使用 Unicode UTF-8 支持全球语言」(ACP=65001)，往返变恒等 → 同一份代码不坏。
不是 Win11 更聪明，是那台机器的 ANSI 代码页碰巧是 UTF-8。

## 审计结论：全仓只有这一处

- `fs::path x = <窄串>` 形式的隐式构造：只有 `userDataDir` 一处；
- 形参是 `const fs::path&` 的函数（`audioFileExists` / `readSusHeader` / `readSidecarMetadata` /
  `folderListing` / `folderFind` / `findSidecar`）调用点全都传 path 变量或 `toFsPath(...)`；
- `path / 窄串` 右侧都是 ASCII 字面量，或 `profileIdFromName()`（会剔掉非 ASCII）与 `version.asset`；
- `ifstream`/`ofstream` 全部走 `toFsPath`。
- AGENTS.md 的「路径一律 UTF-8」那条补了「**隐式构造同样是坑**」+ 审计 grep：
  `grep -rn "fs::path [a-zA-Z_]* *=" game/ platform/ main.cpp`。

## 验证

- `D:\tmp-cn2\中文安装目录\子目录\`（charts 只在 exe 目录）：`[profile] dir` 打印正确，
  `profiles/index.json` 落在 exe 目录；
- 父目录也放一个 charts（走另一条分支）：落在父目录，名字**正确**；
- 两种情形都不再生成乱码目录。

# 第四轮：修另外两处 + 不再往 D 盘根目录扔东西

## 1. 没 3D 驱动时优雅拒绝（main.cpp）

- 机制：`SDL_GL_CreateContext` 在 GDI Generic 上**会成功**（拿到 GL 1.1 上下文），所以
  「上下文为 NULL 就退出」那条守卫不触发；接着 imgui 的 GL3 loader 失败、返回值没人接、
  `NewFrame()` 里 `bd == NULL` → 读 `[NULL+0x30]` → 0xC0000005 @ rva 0xDA3E7。
- 现在：`queryGlVersion()`（**GL_MAJOR_VERSION / GL_MINOR_VERSION 是 3.0 枚举，MinGW 的 1.1
  gl.h 里没有 → 写字面量 0x821B / 0x821C**；老上下文查询失败留下 0 → 回退解析 `GL_VERSION`
  的 `"major.minor"` 前缀）；每次启动打一行
  `[gl] 3.3 | version='…' renderer='…' vendor='…'`；`< 3.3` 走 `reportGlRefusal()`
  （stderr + `MessageBoxW`）后 `return 1`；**接住 `ImGui_ImplOpenGL3_Init()` 的返回值**；
  `--screenshot` 无头跑不弹框（会挂住自检）。
- 调试开关 **`CPSEKAI_FAKE_GL_VERSION=2.1`**：假装版本不够，用来在有显卡的机器上无头验证。
- 实测：本机 `[gl] 3.3 | version='3.3.0 - Build 32.0.101.7088' renderer='Intel(R) Iris(R) Xe Graphics'`
  （正好卡在 3.3 边界，通过）；`CPSEKAI_FAKE_GL_VERSION=2.1` → exit 1 + 中文说明 + 不出截图。

## 2. `cppsekai.log` 被写坏（main.cpp）

- 两条路都在对 **stdout 和 stderr 各做一次 `freopen(..., "w")`**：两个 FILE 各有自己的文件位置
  → 按字节互相覆盖。用户那份日志里 `[dpi] scaling on (per-monitor v2, SDL` 整段没了、只剩
  ` uses DPI scaled points)`，就是一条更长的 stderr 警告从偏移 0 写在了它上面；
  `--screenshot` 那条路还会再 open 一次，把前面已经写好的行整段截掉。
- 统一成 `redirectStdioToLog()`：**只 open 一次** + `_dup2(_fileno(stdout), _fileno(stderr))`
  让 stderr 共用 stdout 的文件描述符 + `gStdioRedirected` 拦住重复打开。
- A/B：把 `assets/se/se_live_perfect.mp3` 改名制造 stderr 早期输出 → 修复后日志 75 行、
  第 1 行是完整的 `[dpi]` 行、SE 警告完整出现在第 27 行、无 NUL 空洞。
- 双击场景用 `subprocess.Popen(creationflags=DETACHED_PROCESS)` 复现（无控制台 → 走启动时的
  重定向那条路），日志同样干净。**注意 Bash 工具不允许调 cmd.exe**，只能用 Python 起进程。

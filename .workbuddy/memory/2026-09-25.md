## chartdl 右侧「下载内容」面板三处修复（用户报：曲目标题被下移、挡到 checkbox）

根因是 09-19 那版 `4ae72f0`（钉住页脚 + 滚动 body）留下的：标题被挪进滚动容器
`gDetailBody`，但坐标仍是**分组框坐标**。

1. **标题挡 checkbox（用户报的）**：`gDetailTitle` 当时用 `createInGroup` 创建（父=body），
   而 `SetWindowPos(gDetailTitle, group, baseX, dp(18), ...)` 里第二个参数是
   *hWndInsertAfter*，不是父窗口 → 实际坐标变成 body 空间，绝对位置 = body(42) + 18 = 60，
   而第一行 checkbox 在 46..70 → 正面压上。
   修：标题改成**分组框的子控件**（`createInBox`），`hWndInsertAfter` 传 nullptr；y=dp(18)
   本来就是分组框坐标，bodyTop=dp(42) 在它下面，语义（滚动行从标题下面滑过）恢复。

2. **空状态整块面板空白**（同一个提交的副作用，用户没提但我顺手修了）：`updateDetailPanel()`
   启动时**根本没人调用**（只有列表选中变化时调），而 `layoutChildren()` 里那句
   `if (gDetailSong >= 0 || gDetailWantedHeight > 0)` 把空状态挡在门外 → 标题、曲绘、
   元数据全是创建时的 10x10，什么都没画。改成无条件调 `layoutDetailRows()`。

3. **「下载内容」标题左边的幽灵 checkbox**：分组框左上角一直有个 ~9x10 的小对勾。
   查法：临时加 `CPPSEKAI_WIN_DUMP` 枚举子窗口 → 那个位置**没有任何窗口**，
   说明是窗口表面上的**陈旧像素**：面板里的控件都是创建即 `WS_VISIBLE`，在第一次布局
   把它们搬走之前先按 10x10 画过一帧，而那块区域后来再没被带擦除地重绘过。
   修：面板内所有行控件**创建时不带 WS_VISIBLE**，由 `placeRow` / 标题那句
   `SetWindowPos` 加 `SWP_SHOWWINDOW` 放出来（空状态另外把 5 个难度框 `SW_HIDE`）。
   顺带给 `saveWindowPng()` 的 `RedrawWindow` 补上 `RDW_ERASE`（原来只有 RDW_INVALIDATE，
   截图会把这种残留一起拍进去，无头自检不能报不存在的像素）。

验证：`--screenshot` + `--select <row>`（这个开关 09-19 就有），旧版对照用
`dist/CppSekai-2026-09-24/chartdl.exe`（18:22 那版更早，连 --select 都没有）。
空/选中/192dpi 三种都截了，`--dpi 192` 下仍是设计内的滚动钳制（expert 行被页脚切一半，
09-19 就确认过是预期）。0 警告。

**可复用的一条**：chartdl 里排查「画面上有东西但枚举不到窗口」→ 先怀疑窗口表面的陈旧像素，
控件级修复是「创建即隐藏」，工具级修复是 `RDW_ERASE`。

## chartdl：最小化再还原，左右两栏宽度自己变了

用户报的现象，根因在 `layoutChildren()`：`gListWidth` / `gBottomHeight` 这两个
**拖出来的宽度**是就地 clamp 的（`gListWidth = clamp(gListWidth, 200, width - …)`），
而最小化时 Windows 发的 `WM_SIZE(SIZE_MINIMIZED)` 带的是 **0x0 客户区**
（用 EnumWindows 查过那个最小化实例：`GetClientRect` = 0,0）→ 一次 0x0 排版就把它们
钉到地板（歌曲列表 200px、日志条 90px），还原后不会自己长回来。
实测：列表右缘 812 → 208（208 = margin 10 + minList 200），385,492 像素变了。

修：`layoutChildren()` 开头 `if (IsIconic(hwnd) || width <= 0 || height <= 0) return;`。
正常缩放碰不到（`WM_GETMINMAXINFO` 卡了 860x560 下限）。

**顺手发现的同类行为（没改，等拍板）**：把窗口拖到 ~890 客户宽以下时，
clamp 会就地改小 `gListWidth`，窗口再放大回去列表**不会**恢复原来的宽度
（实测 812 → 664，放大回来仍是 664）。要修的话得把「用户的偏好宽度」和
「当前能显示的宽度」拆成两个变量，`splitterRects` / `hitSplitter` 也要跟着用后者，
不然热区和实际分割线会错位（那个文件里专门注释过这个坑）。

新增 `.workbuddy/tools/chartdl_minimize_check.py`：真的给运行中的窗口发
`WM_SYSCOMMAND SC_MINIMIZE/SC_RESTORE`，前后各 PrintWindow 一张，断言「列表右缘不变
+ 整图像素 0 变化」；`--no-minimize` 是对照组（什么都不发，证明 diff 不是截图噪声）。
它按 **PID** 认自己启动的实例——chartdl 允许多开，按标题找会抓到别人/残留的窗口
（那个最小化的实例就骗过我一次：客户区 0x0，PrintWindow 直接报 "cannot write empty image"）。

## chartdl：顶栏加「删除文件」按钮

选中一首本地已有文件的曲子时启用（`updateDeleteButton()`，从 `updateDetailPanel()` 与
`refreshDownloadedState()` 调），点击先弹 `MessageBoxW` 确认（**默认按钮是「否」**），
确认后删该曲的 5 张谱面 + 每个演唱版本的 mp3 + 曲绘 + sidecar + 残留 `.part`。
文件名一律走 `chartPath/audioPath/jacketPath/sidecarPath`（和 `queueSong` 同一套，
`sidecarPath()` 是这次新提的 helper，`writeSidecar` 也改用它），所以只按 4 位 id 前缀删，
不会碰到别的曲子。删完 `refreshDownloadedState() → rebuildList() → selectSongRow() →
updateDetailPanel()`，`selectSongRow` 是新的小 helper：`rebuildList` 会丢掉选中行，
不补回去就会「列表无选中、右面板还停在上首歌」。

**顶栏因为多了一个按钮，最小窗口宽度从 dp(860) 提到 dp(930)**（第二行固定按钮排到
dp(784)，`设置…` 从右边 dp(120) 起，客户区需要 dp(902)）。

无头钩子 `--delete-selected`（跳过确认框、真删，务必配 `--out` 指到临时目录）。
新增 `.workbuddy/tools/chartdl_delete_check.py`：真的给窗口 PostMessage 一次点击，
读出确认框文字，两种回答都验（否 → 文件一个都不能少；是 → 只掉选中曲的文件、
同目录别的曲子的文件必须留着），最后把窗口压到最小尺寸、枚举三个按钮的矩形
确认不重叠（问 0x0 尺寸是让 Windows 套用 `WM_GETMINMAXINFO` 最省事的办法）。
实测：确认框文案带曲名与目录 ✓、否 11 个文件不变 ✓、是只留 `0045_*` ✓、
最小尺寸下 取消(616..696) / 删除文件(704..784) / 设置…(794..904) 间隙 8/10 ✓。

## 猜歌：别名画不出来就不出题（2026-09-25）

用户要求：别名里含"范围外字符"就别拿来出题，免得题目变成一堆问号。
做法：新增 `game::fontCoversText(const std::string&)`（`game/Intro.*`），逐码点调
`ImFont::IsGlyphInFont()`；`guessAliasIsUsable()` 里加一条，`buildGuessPool()` 顺便数一下
剔掉多少并在日志里给 3 个例子。实测 **12660 → 11876** 可用（786 条含无字形字符，
如韩文 `텔유월`、`(╯°口°)╯`、开头的制表符），12 次 `--guess` 抽样出的题全部可读。

**关键认知修正**：`GlyphRanges` 在 ImGui 1.92.5 里是 LEGACY（字形按需从字体文件加载，
唯一的门是 `ImFontConfig::GlyphExcludeRanges`，我们没设）。所以"能画什么"取决于 **face 的
cmap** —— `☆`/`碲` 这类范围外但 YaHei 里有的字，游戏里画得出来（抽样抽到过"碲氧"）；
韩文/泰文是字体本身没有 → `?`。选 `IsGlyphInFont()` 而不是
`FindGlyphNoFallback()` 也是因为这个：前者是纯 cmap 查询（不栅格化、不看 atlas 锁），
后者在 atlas 锁定时对**所有**码点都返回 null，而且会真的把上万个字形栅格化进图集。
`fontCoversText()` 在没字体时返回 true（fail open），免得早期调用清空题库。

## 线上崩溃 0xC000001D：构建按 native CPU 编，老机器第一条 AVX-VNNI 就死（2026-09-25 夜）

用户反馈「看到启动画面就静默崩溃」，`cppsekai-crash.log` 只有：异常码 0xC000001D、
`state=-1 glassMode=0 frameless=-1 frames=0`（主循环一帧没跑）、fault rva 0x2113A1。

- `.workbuddy/tools/pe_rva_dump.py` 读那个 RVA 的字节 = `C4 E2 59 52` → **VPDPWSSD**
  （VEX.128.66.0F38.W0 52，AVX-VNNI 的 128 位 int16 点积）。要 Intel 12 代（Alder Lake, 2021）
  起，**AVX2 时代的 Haswell 都不认**。
- 根因：`build.sh` 没给 `-mcpu`，zig 默认目标就是 **native**（`zig c++ -###` 里
  `-target-cpu alderlake`）。09-13 / 09-19 / 09-24 / 09-25 **四个发布版全都带** AVX2/FMA/VNNI。
- 出处：各 TU 编成汇编数 `vpdpwssd` → **`platform/Renderer.cpp` 正好 41 条**（该 TU define 了
  `STB_IMAGE_IMPLEMENTATION`，即 stb_image 的像素解码循环），其余 TU 全 0，与 exe 里扫出的
  41 个 AVX-VNNI 编码一一对应。
- 修：`CXXFLAGS` 加 `-mcpu=baseline`。实测同一份源码：`.text` 3066470 → 2948374、
  VEX 字节 3.80% → **0.36%**（0.36% ≈ 噪音底，纯随机字节命中率约 0.78%）、AVX-VNNI **41 → 0**、
  `.text` 小 119KB；0 error / 0 warning（冷编译）；无头截图冒烟正常（选曲界面完整）。
  最小 hello 也验过 zig 自带的 libc++/libc/compiler-rt 会一起降（native 6956 VEX → baseline 617）。
- 发布闸门：新增 `.workbuddy/tools/cpu_isa_scan.py`（VEX 占比 >1% 或 AVX-VNNI >5 判 FAIL），
  `package.sh` 在 `bash build.sh` 之后自动跑、FAIL 直接 `exit 1` 拒绝打包
  （`CPSEKAI_SKIP_ISA_CHECK=1` 可强行绕过）。拿旧的 09-25 发布包试过，它判 FAIL ✓。
- 顺手清掉的死路（**别再试**）：`CPSEKAI_DEBUG_SYMBOLS` 开关 + `pe_symbols.py`。这套 zig 的 lld
  无论加不加 `-s`/`-g` 都**不写 COFF 符号表**（`PointerToSymbolTable = 0`）、无 `.debug$*` 节、
  `-Wl,-Map=` 被 zig 拒（unsupported linker arg）、`--export-all-symbols`/`--print-map` 被静默吞。
  RVA 只能靠 `pe_rva_dump.py` + `cppsekai.log` 的 `[boot]` 行。main.cpp 那段注释已照实改。
- 还修了 `build.sh` 末尾 `echo "build OK -> build/cppsekai.exe"` 写死、不跟 `OUT=` 走的老毛病。
- 坑（自己踩的）：一边跑 `package.sh` 一边编辑 `build.sh` → bash 是**边读边执行**脚本的，文件当场
  变动导致行错位，报 `build.sh: line 165: comdlg32: command not found`。**改了脚本再跑，别同时动。**

## 0xC000001D 后续：交叉测试工具 + 代际确认（2026-09-25 深夜）

用户联系不上报错的人，但提供两条信息：① 那台生成 release 的机器是 **i3-7100U**（7 代 Kaby Lake）；
② 报错用户是 **Win11**。于是做了三件事：

- **构建机确认**：本机 `PROCESSOR_IDENTIFIER` = Family 6 **Model 154** Stepping 3 = **i7-1260P**
  （Alder Lake-P 12 代），和 zig `-###` 里的 `-target-cpu alderlake` 完全对上。所以本机 dist/
  四个包全都是这台编的（每个包 exe 里都扫出 41 条 AVX-VNNI —— 若真在 Kaby Lake 上编过，绝不会有）。
- **代际确认（Key fact）**：`AVX-VNNI` 是 **VEX 编码**的 VNNI，Intel 从 **12 代 Alder Lake（2021 Q4）**
  才有，AMD 要 **Zen 5（2024）**；**`AVX512-VNNI` 是另一回事**（10/11 代 Intel、Zen 4 都有）。
  所以"能装 Win11"完全不影响中招：Intel 8 代 ~ 11 代、AMD Zen 2/3/4 全都跑不了旧包。
  报错用户是 Win11 恰恰符合这个画像。
- **新工具**：`.workbuddy/tools/cpu_features.c` → `build/cpuinfo.exe`（**必须 `-mcpu=baseline` 编**，
  否则它自己在要诊断的机器上先崩）。双击报 CPU 型号 + SSE2/AVX2/FMA/BMI2/AVX512-VNNI/AVX-VNNI，
  并按"旧包要 AVX-VNNI、新包只要 SSE2"判能不能跑；exe 路径当参数传进去还会扫那份 exe 的
  VEX 占比 / AVX-VNNI 条数。实测 i7-1260P：AVX-VNNI **有**（本机复现不了崩溃）。
  交叉测试包在 `dist/_cpucheck/`（cpuinfo.exe + 说明.txt，dist 被 gitignore）。
- 工具自身的坑（两个，都是我自己写的）：① 扫描用的三个累加器**没在文件之间清零**，
  三份文件的数字叠在一起还"看起来很合理"（正好等于 09-24+09-25 的 .text 之和），
  害我怀疑 PE 解析；② 修的时候用了多行 `/* ... */`，**注释把后两条赋值语句吃进去了**，
  于是只有第一个变量被清零。**别把注释夹在赋值中间。**
- 顺便验证了 `dist/CppSekai-2026-09-13.zip` 是 2.8MB（不带 assets 的精简包），
  09-19 / 09-24 / 09-25 是 7MB 全量包 —— 交叉测试用 **09-24**（最后一个含 VNNI 的全量包）。
